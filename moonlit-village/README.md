# 月下疑云 / Moonlit Village

## 预言家必须附查验结果，取消纯身份起跳（2026-10-31）

- **发言菜单与房主校验：** 移除不附任何结果的「直接跳预言家」发言选项；房主同样拒绝此旧式动作。公开预言家身份需要选择「金水」或「查杀」，指明对象与查验夜晚。原有旧身份宣称的读取与多语言文字保留为历史兼容，不再是可执行新发言。
- **死者也可被引用：** 真预言家第一晚查到的人若当晚被狼人杀死，依然可以报告这次查验；查验结果对好人阵营已无新增阵营信息，但报出原始夜晚可以让身份宣称可被核对。客户端在查验报告选人时允许点选已出局角色；普通怀疑、站边、投票仍限制为存活对象。
- **好人挡刀假跳：** AI 村民和守卫仍可能策略性伪装。若假跳预言家，AI 只会选用夜间遇袭、已经公开确认好人阵营的死者编造有夜晚的金水，不凭空报查杀、不给不确定的活人发金水。村民假跳守卫仍可独立执行。
- **一致性与信息隔离：** 真实预言家的报告只能来自其私人历史查验；其他身份可编造报告，但不得声称在公开死亡之后的夜晚查验死者。AI 的计划、公开发言与房主接收会传递同一个查验日期；他人不会因此获得真实身份或夜间行动。
- **验证：** JavaScript 语法检查、菜单移除、真预言家历史死者查验、守卫挡刀金水、虚构查验时序拒绝、伪造真实预言家结果拒绝、真人历史查验目标选择、AI 实际发言保留夜晚等模拟检查通过。尚未完成真实双设备浏览器对局测试。


## 六人局：查验对象夜死不再使 AI 预言家潜伏（2026-10-31）

- **确定信息：** 本模式只有一狼且禁止自刀，也没有女巫等额外夜杀。夜间遇袭出局者的好人阵营已被游戏公开确认；预言家查到该人的「好人」结果不提供额外阵营信息。
- **AI 预言家首日起跳：** 六人单预言家配置中，存活的 AI 预言家即使只查到夜间死者，仍会公开声明预言家身份；有存活查杀、存活金水时优先报告实际查验。绝不将「查验对象已死」作为 AI 随机不跳的理由。死亡的预言家无法发言。
- **好人推理：** 存活 AI 预言家在有发言机会时首日未跳，会降低后续「其为真正预言家」假设的权重；首夜已遇袭出局的预言家没有发言机会，不产生这一惩罚。真人预言家仍可自选潜伏，因此首日无人起跳只能提高「预言家可能已死」的可信度，**不能证明**死亡身份。
- **验证：** JavaScript 语法检查、死亡查验目标首日正常起跳、查到狼人报查杀、查到存活好人报金水、八人板不强制套用六人规则、预言家在首次发言前死亡免受沉默惩罚，以及真人主动潜伏与 AI 沉默采用不同证据权重的模拟测试通过。


## 放逐与狼人 AI 的风险博弈（2026-10-31）

- **投票规则：** 取消必须至少两票才能放逐的额外门槛。只要存在唯一最高票，即使全场只有一人投票，该对象也会被放逐。全员弃权、票数平局都无人放逐。放逐后仍按原有阵营胜负条件结算。
- **先投票、后统一公开：** 白天投票期间，房主私下记录各真人、AI 及超时弃权选择；待所有存活玩家提交或到期才统一写入公开日志与票型账本。不能提前看见他人的真实本轮选票，也避免 AI 利用本轮秘密投票。多人局的原有两分钟限制保留。
- **狼人白天投票策略：** 狼人不再无条件投票。公开怀疑、过去的公开票型、是否被查杀、场上人数、可能成为唯一投票者的曝光风险、自己是否已独票放逐好人等因素会影响决策。第一天通常谨慎，但允许小概率冒险单票推人；三人残局和强烈压力下更可能放手一搏。不会读取 `st.votes` 中其他玩家尚未公开的选择。
- **狼人夜袭策略：** 公开预言家宣称只是重要线索，不是系统确认身份。AI 同时估计可能被守卫保护、刚刚投票同一目标带来的关联风险、前一夜对该目标的袭击是否失败，并随机选择较有价值的目标，避免必定昼票夜刀同一人。
- **好人如何看独票：** 独票放逐一名被公开证明为好人的玩家会成为后续可核对的票型线索，并小幅增加投票者的可疑度，但不被视作狼人铁证，好人也可能判断失误。
- **验证：** 通过单票放逐狼人／好人、全员弃权、平票、两票放逐等5项计票模拟；6种白天狼人风险决策情境及2种夜袭分布模拟；完成一次包含真人提交、AI 投票、统一公开和单票放逐的状态机模拟。尚未进行真实双人联机或手机端完整对局测试。


## 白天选项与证据机制重构（2026-10-31）

- **四个主入口：** 白天真人发言改成「公开身份与查验」「指出嫌疑」「表达信任」「暂不表态」。身份菜单保留预言家、守卫、村民宣称及金水／查杀；旧发言类型保留在 AI 和历史记录中兼容，不作为真人重复菜单。
- **公开证据可选：** 怀疑与信任先选人，再从该人真正的公开跳身份、查验报告和投票记录中选择一项引用，或明确选择「仅凭推测」。每个引用通过 `publicEvents.seq` 关联，在房主侧验证事件发言人，禁止将他人的记录冒充为被指对象的行为。引用是引用，不等于记录为真；已撤回的身份／报告在证据选择处明确标记。
- **真实预言家报查验：** 对存活且此前确实查验过的目标选择金水或查杀，再选择真实查验发生的夜晚；房主核对私有 `known`，不可伪造夜晚、结果或不存在的查验。其他身份仍可以按照狼人杀规则假跳身份并虚报查验，需要明确选择声称的夜晚。报告展示与历史记录记下的夜晚不再默认取当天。
- **质疑回应：** 移除将「解释／反驳／承认／回避」直接转换为固定嫌疑分数的机制。被质疑者现在可撤回**被质疑的具体发言**（而非无关声明），原始记录保留并在回应事件中留下撤回标记。AI 对撤回声明不再作为当前有效身份宣称加权，但历史矛盾不会被抹除；推理缓存随撤回刷新。历史投票不能撤销。
- **兼容与约束：** 保留房主验证、多人同步、夜间流程、原有六人身份结构和三种语言。六人局规则没有改成其他板子。旧页面仍开的玩家应刷新，以便客户端与房主使用相同的新增发言字段。
- **验证范围：** 已进行 JavaScript 语法检查、证据引用归属／伪造拒绝、旧夜查验及错误查验拒绝、假跳允许、证据菜单筛选与提交可用性等模拟断言；检查 AI 原有的具体推理台词未被新版无证据文字覆盖。尚未完成真实手机触屏和双设备网络联机回归测试。


### 音效延迟修复（2026-10-30）

以前每种音效首次触发时才通过 `new Audio(path)` 建立播放器，并在后续每次触发时执行 `pause() → currentTime=0 → play()`，在移动 Safari 上容易出现明显的解码或音频管线启动延迟。

现在页面加载时通过 `fetch() + AudioContext.decodeAudioData()` 预取、解码六个音效，常规点击直接用 `AudioBufferSourceNode.start(0)` 播放。首次触摸时尝试解锁 iOS AudioContext；音效尚未准备好时跳过当次，不在玩家进入下一步之后补播。对 cursor、confirm、cancel、damage 做轻量前置静音检测和处理（最多扫描 280ms），避免原始音效里的开头静音造成“慢一拍”。没有修改音效的艺术内容。

右上角开关依旧同时控制 BGM 和 SFX，并立即停止当前正在发声的节点。浏览器缺少 AudioContext 时使用预加载的 HTML Audio 作为兼容回退。实际触屏响应速度仍受设备、浏览器与系统音频输出延迟影响。

## 终局全员身份揭晓与预言家查验记录（2026-10-31）

- **游戏结算：** 当房主判定一方获胜、同步 `phase === "ended"` 后，每位玩家都会自动看到六名居民的身份揭晓表，包含头像、玩家昵称、职业（狼人／预言家／守卫／村民）和最终存活状态。中央对话记录与原有结算操作保留；关闭弹窗后，可按 **查看全员身份 / View all identities** 再次打开。重新开局时关闭旧揭晓，下一局重新抽牌。
- **结果保密边界：** `snapshot(id)` 在对局结束前始终返回所有玩家的公开状态和 `role:null`，只有 `phase === "ended"` 时公开每个人的真实职业。任何结局列表都只从这份已完成状态构造，绝不从公开投票或 AI 内部数据猜测身份。
- **预言家查验：** 夜间成功查验时，`finishNight()` 把被查验玩家的**具体职业**写入该预言家私有的 `st.known[seer.id]`。发给玩家的 `snapshot(id).knowledge` 只有当接收者是预言家本人时才包含历史记录。预言家在主界面能看到已查验居民的职业标签、最近的查验结果，并能通过 **查验记录 / Inspection history** 查看全部历史；其他角色和所有玩家的公开记录里都不会出现这些秘密结果。
- **UI 与语言：** 两个弹窗都具备 English／简体中文／日本語翻译，并支持 Esc 关闭和键盘焦点返回。六人身份列表的名字进行 HTML 转义，以防玩家输入的昵称被当作标记执行。此前只提示“好人／狼人”的查验信息现改为显示职业名。
- **验证：** 测试了夜间查验守卫时记录正确职业、预言家与其他角色的私有快照隔离、非结局禁止展开全员身份、结局六人一次性揭晓、关闭后不自行重弹、手动重新打开，以及返回房间时清理结果。当前仅为模拟验证，真实手机与网络联机仍需人工检查。

## 开局确认、夜间顺序等待与多人限时（2026-10-31）

- **多人抽牌：** 房主开始游戏后进入 `deal`，每位真人只能看到自己的秘密身份，全部真人翻开并确认才进入第一夜。等候确认期间不强制两分钟结束；有人断线被 AI 接管后，不再等待该人的确认。
- **夜间始终按固定顺序提示：** **等待狼人行动 → 等待预言家行动 → 等待守卫行动**。三轮等待及秒数现在显示在**中央故事对话框**中，覆盖夜间历史记录，不再占据顶部状态栏。每一个提示都会按固定时长出现，不因对应职业是否存活、玩家是否已经提交而跳过，因此不能通过提示的出现/消失推断角色身份。中间的战报只显示「夜间行动开始」，不再同时列出三种职业。未引入女巫。
- **只有一名真人（单人模式、或联机房间仅剩一名真人）：** 完全**没有两分钟行动限制**，左下角的 02:00 倒计时隐藏。每个公开夜间提示只等待 **2 秒**，带有“剩余2秒→剩余1秒”的倒计时；三个提示至少 **6 秒**。真人需要选择夜间技能时可继续思考，六秒过后显示通用的“等待剩余夜间行动”，不会强迫该真人弃权。白天发言和投票同样不限时。
- **至少两名真人的多人模式：** 夜间、发言、投票各阶段**共用两分钟**截止时间，房主统一执行超时或拒绝迟到的操作。公开夜间提示每个 **4 秒**，最短 12 秒才进入下一阶段。夜间技能未提交视为不使用，发言未提交视为不表态，投票未提交视为弃票；全员弃票无人放逐。
- **系统同步：** `armPhaseTimer()` 判断真人数量，`snapshot()` 提供相对耗时和 `deadlineActive` 标记，`updatePhaseHud()` 根据模式切换提示间隔与剩余秒数。仅一名真人留下时，原多人截止时间会取消；AI 行动仍可自动完成，公开顺序依然固定。全程不广播任何其他人的秘密身份。

已通过单/多人时限单元测试：单人公开轮次 0、2、4 秒切换（2/1 秒倒计时），多人为 0、4、8 秒切换（两分钟计时显示），单人不创建超时定时器、多人创建 120000ms 定时器。此前通过的身份确认、超时弃票和联机对局测试仍适用。真实 iPhone 与真实多人网络环境还需要人工验收。

## 音量与真人玩家自定义头像（2026-10-31）

顶部齿轮 **Settings / 设置 / 設定** 可随时打开设置面板。**这里仅调整声音**：分别用 `bgmVolume` 和 `effectsVolume` 调整背景音乐与操作音效，范围 0–100。数值存储在各自浏览器的 `localStorage`，右上角原有的音乐开关仍可一键暂停或恢复全部声音。

**真人玩家的头像只能在开局前的首页选择。** 昵称输入框下方是 `home-avatar-picker`：从电脑硬盘或手机相册选择 PNG、JPEG、WebP（每张小于 8 MB），也可以直接使用随机预设头像。首页会立即显示所选头像预览；玩家确认后才点击 **Solo / Create room / Join room** 进入游戏。上传图片处理期间，三个进入游戏按钮暂时不可点击，避免未完成压缩就开始游戏。进入游戏后，头像不再通过音量设置更改。

客户端在本机将图片裁成方形，并压缩成小于约 26 KB 的 data URL，作为公开头像发送给同房间的其他玩家。用户上传图片保存在本人浏览器的 `moonlit-avatar` 中，联机时通过原有 PeerJS 连接共享；**没有额外的上传服务器**。请勿选用不愿展示给同房间其他人的私人照片。

不上传、或点击 **Random preset portrait / 随机预设头像**，就会随机选用六张学院肖像素材之一，首页预览与进入游戏后的头像一致。AI 人物也使用随机预设肖像，但**没有头像上传功能**。居民站位、中央发言框、投票目标卡共用同一张头像，并且不根据狼人身份或其他秘密角色决定头像。房主发起下一局时仍保留真人已选择的头像；玩家掉线被 AI 接管后，房间停止展示该真人上传的头像。

主要接口：`faceMarkup()`、`resizeAvatar()`、`applyOwnAvatar()`、`randomPortrait()`、`snapshot()`。头像只在首页选择并由创建/加入房间流程发送，音量可在游戏中随时调整。修改的只是公开外观状态；不修改胜负规则、隐藏身份、发言或投票处理。浏览器禁用本地存储时，选择可在当前页面运行，但刷新后不会保留。

## 多语言支持 / Localization (English · 简体中文 · 日本語)

游戏首次访问默认 **English**。顶栏左侧可以切换 **EN / 中文 / 日本語**；选择保存在浏览器 `localStorage` 的 `moonlit-language` 中。清空网站存储或首次在新浏览器打开时恢复英语默认值。设置只保存在本设备，不会修改好友的语言。

翻译词库位于 `moonlit-village/index.html` 的 `translations.en / translations.zh / translations.ja`，涉及首页、角色与能力、抽牌、昼夜动画、系统公告、发言、投票、结算、错误提示和可访问性标签；代码中的 `applyStaticLanguage()`、`render()`、`localizeLog()`、`localizeSpeech()` 以及 `updateLanguageOverlays()` 负责显示更新。用户自己输入的昵称不会自动翻译。

**多人模式兼容：** 房主仍以原有规范化的消息和角色 ID 传输游戏状态。客户端收到状态后自行翻译显示，不会因语言不同修改角色分配、AI 策略、投票或秘密身份。六名预设电脑玩家的名字可显示为本地化名称，但内部名字仍保持原来的唯一标识。若系统出现无法识别的新增公告，暂时回退原始消息以避免误译。
